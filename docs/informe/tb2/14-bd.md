# 14. Bases de datos

El sistema usa dos bases con papeles distintos. **MongoDB** es la persistencia: modelos publicados, entrenamientos, registro de predicciones y usuarios. **Redis** es la caché de predicciones. La API solo conoce dos interfaces de Go, `almacen.Almacen` y `almacen.Cache`, con una implementación en memoria para los tests y otra con los drivers oficiales de MongoDB y Redis (MongoDB, Inc., 2025; Redis Ltd., 2025), los únicos paquetes de terceros del proyecto (ADR-0003). Esta sección describe las entidades (14.1), las claves de Redis (14.2), la escritura asíncrona (14.3) y, en respuesta a la observación 6 de la PC4 («imágenes de BD: ¿qué evidencian?»), qué prueba cada línea de la evidencia (14.4).

## 14.1 MongoDB: colecciones, documentos e índices

La base `cc65_dengue` tiene cuatro colecciones (@fig:entidades y @tab:colecciones). Se eligió un modelo de documentos porque las entidades tienen arreglos de tamaño variable (pesos, pérdida por época, nodos) que se leen y escriben enteros: en una base relacional serían tablas intermedias que siempre se consultan juntas.

Tabla: Colecciones de MongoDB {#tab:colecciones}

| Colección | `_id` | Qué guarda | Índices | Para qué consulta |
|---|---|---|---|---|
| `modelos` | Versión: 12 caracteres hexadecimales del SHA-256 del modelo | Pesos, esquema de variables, umbral, ajuste de calibración, fecha de publicación y el resumen de cada entrenamiento que lo publicó | `{publicado: −1}`, `{entrenamientos.id: 1}` | Cargar el modelo vigente al arrancar; encontrar el modelo de un entrenamiento |
| `entrenamientos` | `ent-<fecha>-<aleatorio>` | Estado, parámetros, época actual, pérdida por época, nodos, reasignaciones, inicio, fin y versión del modelo publicado | `{inicio: −1}`, `{estado: 1}` | Listar los últimos; encontrar los que quedaron en curso tras un reinicio |
| `predicciones` | `ObjectId` | Fecha, versión del modelo, consulta normalizada, riesgo, clase, si salió de la caché y microsegundos | `{fecha: −1}` con vencimiento (TTL), `{version_modelo: 1, consulta.departamento: 1}` | Auditar qué se predijo con cada modelo y en qué departamento |
| `usuarios` | Correo | Hash PBKDF2 de la clave, rol y fecha de alta | El propio `_id` (único) | Iniciar sesión |

Nota: Elaboración propia a partir de `internal/almacen/almacen.go`, `usuarios.go` y `(*Almacen).crearIndices`.

**Relaciones.** Un entrenamiento terminado guarda la versión del modelo que publicó; el modelo guarda, embebido, el resumen de cada entrenamiento que lo publicó; cada predicción guarda la versión del modelo con que se calculó, y la clave de la caché también la incluye. Así se puede seguir la cadena completa en las dos direcciones: entrenamiento → modelo → predicciones → claves de caché, que es lo que comprueba la evidencia de la sección 14.4.

Cada colección corresponde a un `struct` de Go con etiquetas `bson`, que el driver codifica y decodifica directamente:

**Publicación atómica del modelo.** Publicar un modelo no reemplaza el documento: `GuardarModelo` hace una sola operación `UpdateOne` con *upsert*. `$setOnInsert` escribe pesos y esquema solo si la versión es nueva, `$push` agrega el resumen del entrenamiento y `$max` adelanta la fecha de publicación. Dos entrenamientos que llegan a los mismos pesos comparten la versión sin pisarse:

<!-- generado:fuente:internal/almacen/mongo/mongo.go#(*Almacen).GuardarModelo -->
```go
// internal/almacen/mongo/mongo.go
// GuardarModelo es un solo UpdateOne con upsert, atómico sobre el documento:
// inserta los campos del modelo si la versión es nueva ($setOnInsert), agrega
// los resúmenes de entrenamiento ($push) y adelanta publicado ($max).
func (a *Almacen) GuardarModelo(ctx context.Context, m almacen.Modelo) error {
	resumenes := m.Entrenamientos
	if resumenes == nil {
		resumenes = []almacen.ResumenEntrenamiento{}
	}
	cambio := bson.D{
		{Key: "$setOnInsert", Value: bson.D{
			{Key: "pesos", Value: m.Pesos}, {Key: "esquema", Value: m.Esquema}, {Key: "umbral", Value: m.Umbral},
			{Key: "ajuste_prior", Value: m.AjustePrior}, {Key: "generado", Value: m.Generado},
		}},
		{Key: "$max", Value: bson.D{{Key: "publicado", Value: m.Publicado}}},
		{Key: "$push", Value: bson.D{{Key: "entrenamientos", Value: bson.D{{Key: "$each", Value: resumenes}}}}},
	}
	_, err := a.modelos.UpdateOne(ctx, bson.D{{Key: "_id", Value: m.Version}}, cambio, options.UpdateOne().SetUpsert(true))
	if err != nil {
		return fmt.Errorf("mongo: modelos: %w", err)
	}
	return nil
}
```

```go
// internal/almacen/mongo/mongo.go
func (a *Almacen) crearIndices(ctx context.Context) error {
	indices := []struct {
		col    *drv.Collection
		models []drv.IndexModel
	}{
		{a.modelos, []drv.IndexModel{
			{Keys: bson.D{{Key: "publicado", Value: -1}}},
			{Keys: bson.D{{Key: "entrenamientos.id", Value: 1}}},
		}},
		{a.entrenamientos, []drv.IndexModel{
			{Keys: bson.D{{Key: "inicio", Value: -1}}},
			{Keys: bson.D{{Key: "estado", Value: 1}}},
		}},
		{a.predic, []drv.IndexModel{
			{Keys: bson.D{{Key: "fecha", Value: -1}},
				Options: options.Index().SetExpireAfterSeconds(DiasRegistroPredicciones * 24 * 3600)},
			{Keys: bson.D{{Key: "version_modelo", Value: 1}, {Key: "consulta.departamento", Value: 1}}},
		}},
	}
	for _, i := range indices {
		if _, err := i.col.Indexes().CreateMany(ctx, i.models); err != nil {
			return fmt.Errorf("mongo: índices de %s: %w", i.col.Name(), err)
		}
	}
	return nil
}
```

**Consistencia ante fallos.**

- **El modelo se publica solo si quedó guardado.** Si la escritura falla, el entrenamiento queda `fallido` y sigue publicado el modelo anterior.
- **Un reinicio no deja entrenamientos colgados.** Al arrancar, los que quedaron `en_curso` pasan a `terminado` si su modelo se guardó, o a `fallido` si no (`reconciliar`).
- **Dos coordinadores no se pisan.** Los entrenamientos se crean con inserción, no con *upsert*: un identificador repetido devuelve error y se reintenta con otro.
- **Las credenciales no se filtran.** Los errores de conexión muestran solo el esquema y los servidores de la URI, nunca el usuario ni la clave.

## 14.2 Redis: claves, TTL e invalidación

Redis guarda el JSON de cada predicción calculada, con una vigencia fija (TTL), bajo una clave que se arma así:

<!-- generado:fuente:internal/almacen/almacen.go#ClavePrediccion -->
```go
// internal/almacen/almacen.go
// ClavePrediccion arma la clave de Redis. Incluye la versión del modelo: un
// modelo nuevo usa claves nuevas, así que publicar invalida la caché.
func ClavePrediccion(version string, c ConsultaNormalizada) string {
	return fmt.Sprintf("pred:%s:%s:%d:%d:%s:%s", version, c.Departamento, c.Ano, c.Semana,
		strconv.FormatFloat(c.EdadAnios, 'g', -1, 64), c.Sexo)
}
```
<!-- /generado -->

- **Normalización.** La clave se arma con la consulta ya validada por las reglas de la limpieza, que normalizan el departamento y llevan la edad a años: `"loreto"` y `"LORETO"`, o 12 meses y 1 año, comparten la misma entrada.
- **Invalidación por versión.** La clave incluye la versión del modelo. Cuando se publica un modelo nuevo, las predicciones del anterior dejan de encontrarse, porque las nuevas claves llevan otra versión, y las viejas expiran solas por su TTL. No hace falta borrar nada ni coordinar la caché con el entrenamiento.
- **Presupuesto de tiempo.** Leer y escribir en Redis tienen cada uno un plazo fijo. Si Redis está lento o caído, la API calcula la predicción y responde igual: la caché acelera, pero nunca es necesaria para responder (*cache-aside*, ADR-0006).

## 14.3 Escritura asíncrona con búfer

Cada predicción se registra en MongoDB, pero la respuesta no espera a la base. El handler deja el registro en un canal con búfer (`registrar`) y una sola goroutine (`registrador`) lo consume y escribe con su propio plazo. Es el patrón **productor-consumidor** con un búfer acotado:

<!-- generado:fuente:internal/api/api.go#(*Servidor).registrar -->
```go
// internal/api/api.go
// registrar encola sin bloquear.
func (s *Servidor) registrar(r almacen.RegistroPrediccion) {
	select {
	case s.registros <- r:
	default:
		s.descartados.Add(1)
	}
}
```
<!-- /generado -->

<!-- generado:fuente:internal/api/api.go#(*Servidor).registrador -->
```go
// internal/api/api.go
// registrador es el único consumidor de s.registros. El canal nunca se cierra
// (los handlers podrían enviar después): termina con el contexto y antes
// vacía lo que quede, hasta que venza el plazo de cierre.
func (s *Servidor) registrador() {
	defer s.wgRegistrador.Done()
	guardar := func(r almacen.RegistroPrediccion) {
		ctx, cancelar := context.WithTimeout(s.ctxDrenaje, plazoRegistro)
		defer cancelar()
		if err := s.op.Almacen.RegistrarPrediccion(ctx, r); err != nil && s.ctxDrenaje.Err() == nil {
			s.op.Log("api: no se pudo registrar la predicción: %v", err)
		}
	}
	for {
		select {
		case r := <-s.registros:
			guardar(r)
		case <-s.ctx.Done():
			for {
				if s.ctxDrenaje.Err() != nil {
					n := int64(len(s.registros))
					s.descartados.Add(n)
					s.op.Log("api: venció el plazo de cierre; %d registros sin escribir", n)
					return
				}
				select {
				case r := <-s.registros:
					guardar(r)
				default:
					return
				}
			}
		}
	}
}
```
<!-- /generado -->

El `select` con `default` es lo que hace que el productor nunca se bloquee: si el búfer está lleno porque MongoDB está lento, el registro se descarta y se cuenta (`no_registradas` en `GET /api/v1/cluster`), y la predicción se responde igual. Se eligió perder un registro de auditoría antes que demorar una respuesta, porque el requisito de latencia es del servicio y el registro es secundario. Al cerrar el servidor, el consumidor vacía lo que quedaba en el búfer antes de terminar, con un plazo máximo de cierre; lo que no alcanza a escribir también se cuenta como no registrado.

Qué prueba cada parte de la salida:

1. **Documentos e índices de cada colección.** Las cuatro colecciones existen y tienen los índices de la @tab:colecciones, incluido el TTL de `predicciones` (en segundos). Prueba que el esquema descrito es el que está en la base, no solo en el código.
2. **Usuarios por rol y claves como hash.** Cuántos usuarios hay de cada rol, y que todas sus claves están guardadas como hash PBKDF2-SHA256: ninguna en texto plano. El guion no imprime correos ni hashes.
3. **Cadena del entrenamiento.** El último entrenamiento terminado tiene estado `terminado`, sus épocas completas, su pérdida final, sus nodos y sus reasignaciones. Prueba que la API persiste el entrenamiento que lanzó.
4. **Modelo publicado.** Existe un documento en `modelos` cuyo `_id` es la versión que guardó el entrenamiento **y** que contiene el resumen de ese entrenamiento (`entrenamientos.id`). Prueba la referencia en las dos direcciones.
5. **Predicciones con esa versión.** Hay predicciones registradas con la versión del modelo, y una parte salió de la caché (`desde_cache`). Prueba que la escritura asíncrona funciona bajo la carga del benchmark y que cada predicción queda asociada al modelo con que se calculó.
6. **Claves en Redis.** Existen claves `pred:<versión>:*` y la primera tiene un TTL positivo. Prueba que la caché usa la versión del modelo en la clave y que las entradas vencen solas.

En conjunto, la evidencia muestra la cadena completa de la @fig:entidades con datos reales del sistema desplegado: entrenamiento → modelo → predicciones → caché.
