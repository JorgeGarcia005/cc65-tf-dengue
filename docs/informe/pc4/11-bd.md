# 11. Bases de datos

## 11.1 Rol de cada base

| Base | Rol | Por qué |
|---|---|---|
| **MongoDB** | Persistencia: modelos publicados, entrenamientos y registro de predicciones | Los documentos tienen arreglos de tamaño variable (pesos, pérdida por época, nodos) que se guardan enteros, sin tablas intermedias, y el modelo vigente se obtiene con un índice por fecha de publicación |
| **Redis** | Caché de predicciones | Una predicción repetida se responde desde memoria; las claves incluyen la versión del modelo y expiran solas |

La API solo conoce las interfaces `almacen.Almacen` y `almacen.Cache` (`internal/almacen`); hay una
implementación en memoria para los tests, y las de MongoDB y Redis con los drivers oficiales (MongoDB,
Inc., 2025; Redis Ltd., 2025), los únicos terceros del proyecto (ADR-0003). Las decisiones están en `docs/decisiones/ADR-0006-entidades-mongo-redis.md`.

## 11.2 Entidades (MongoDB, base `cc65_dengue`)

| Colección | `_id` | Campos principales | Índices |
|---|---|---|---|
| `modelos` | versión (12 hex del sha256 del modelo) | pesos, esquema de variables (departamentos, medias, desviaciones), umbral, ajuste de calibración, fecha de publicación y el resumen de cada entrenamiento que lo publicó | `{publicado: -1}` para el vigente; `{"entrenamientos.id": 1}` |
| `entrenamientos` | `ent-<fecha>-<aleatorio>` | estado (`en_curso`, `terminado`, `fallido`), épocas, tasa, λ, época actual, pérdida por época, nodos y reasignaciones, inicio, fin, versión del modelo publicado | `{inicio: -1}`, `{estado: 1}` |
| `predicciones` | ObjectId | fecha, versión del modelo, consulta normalizada, riesgo, clase, si salió de la caché y microsegundos | `{fecha: -1}`, `{version_modelo: 1, "consulta.departamento": 1}`, TTL de 90 días |

**Relaciones.** Un entrenamiento terminado apunta a la versión del modelo que publicó; el modelo guarda el
resumen de los entrenamientos que lo publicaron; cada predicción guarda la versión del modelo con que se
calculó. Así se puede seguir la cadena completa: entrenamiento → modelo → predicciones → claves de caché.

## 11.3 Claves de Redis

| Clave | Valor | Vigencia |
|---|---|---|
| `pred:<versión>:<departamento>:<año>:<semana>:<edad en años>:<sexo>` | JSON de la predicción | 24 horas |

La consulta se normaliza antes de armar la clave, así que `"loreto"` y `"LORETO"`, o 12 meses y 1 año,
comparten la entrada. Publicar un modelo nuevo invalida la caché sin borrar nada: las claves llevan la
versión y las viejas expiran.

Los índices se crean al conectar, en `crearIndices`; el de `fecha` en `predicciones` es un índice TTL que
borra los registros de más de 90 días:

<!-- generado:fuente:internal/almacen/mongo/mongo.go#(*Almacen).crearIndices -->
```go
// internal/almacen/mongo/mongo.go
func (a *Almacen) crearIndices(ctx context.Context) error {
	indices := []struct {
		col    *drv.Collection
		models []drv.IndexModel
	}{
		{a.modelos, []drv.IndexModel{
			{Keys: bson.D{{Key: "publicado", Value: -1}}},
			{Keys: bson.D{{Key: "entrenamientos.id", Value: 1}}},
		}},
		{a.entrenamientos, []drv.IndexModel{
			{Keys: bson.D{{Key: "inicio", Value: -1}}},
			{Keys: bson.D{{Key: "estado", Value: 1}}},
		}},
		{a.predic, []drv.IndexModel{
			{Keys: bson.D{{Key: "fecha", Value: -1}},
				Options: options.Index().SetExpireAfterSeconds(DiasRegistroPredicciones * 24 * 3600)},
			{Keys: bson.D{{Key: "version_modelo", Value: 1}, {Key: "consulta.departamento", Value: 1}}},
		}},
	}
	for _, i := range indices {
		if _, err := i.col.Indexes().CreateMany(ctx, i.models); err != nil {
			return fmt.Errorf("mongo: índices de %s: %w", i.col.Name(), err)
		}
	}
	return nil
}
```

La clave de Redis sale de la misma consulta normalizada y de la versión del modelo:

<!-- generado:fuente:internal/almacen/almacen.go#ClavePrediccion -->
```go
// internal/almacen/almacen.go
// ClavePrediccion arma la clave de Redis. Incluye la versión del modelo: un
// modelo nuevo usa claves nuevas, así que publicar invalida la caché.
func ClavePrediccion(version string, c ConsultaNormalizada) string {
	return fmt.Sprintf("pred:%s:%s:%d:%d:%s:%s", version, c.Departamento, c.Ano, c.Semana,
		strconv.FormatFloat(c.EdadAnios, 'g', -1, 64), c.Sexo)
}
```

## 11.5 Consistencia ante fallos

- **El modelo se publica solo si quedó guardado.** La misma escritura guarda el modelo y el resumen del
  entrenamiento; si falla, el entrenamiento queda `fallido` y sigue publicado el anterior.
- **Un reinicio no deja entrenamientos colgados.** Al arrancar, los que quedaron `en_curso` pasan a
  `terminado` (con su resumen) si su modelo se guardó, o a `fallido` si no.
- **Dos coordinadores no se pisan.** Los entrenamientos se crean con inserción, no con *upsert*: un ID
  repetido devuelve error y se reintenta con otro.
- **Las credenciales no se filtran.** Los errores de conexión muestran solo el esquema y los hosts de la URI.

`scripts/evidencia-bd.sh <id>` verifica en la base real la cadena de un entrenamiento del clúster
(entrenamiento terminado → modelo con ese `_id` → predicciones de esa versión → claves con TTL en Redis) y
falla si falta un eslabón. Su salida está en la sección 12.4.
